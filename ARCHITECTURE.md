# Архитектура Customer Orders Platform

Customer Orders Platform подготавливает контур приёма и обработки заказов клиентов. Сейчас реализована инфраструктура; прикладной backend и форма заказа запланированы.

## Компоненты

```text
Клиент → HTTPS orders.example.com → Traefik → Nginx
                                              └─ /api → 503 до появления backend

PostgreSQL ← pgAdmin ← localhost VPS ← SSH-туннель администратора

GitHub Actions → HTTPS docker-registry.example.com → Traefik → Registry → том образов
       └─ Coolify API → WEB_IMAGE с digest → деплой → проверка версии Nginx
```

Registry и приложение разворачиваются как два независимых Docker Compose-ресурса Coolify. Registry использует официальный образ Distribution, а не образ, который хранит сам. Данные Registry, PostgreSQL и pgAdmin находятся в постоянных томах.

Traefik обслуживает внешний HTTP/HTTPS и сертификаты. Nginx отвечает за веб-часть проекта. Registry подключается напрямую к Traefik. PostgreSQL доступен только в сети database; наружу его порт не публикуется. pgAdmin имеет привязку только к loopback-интерфейсу VPS. В Coolify не назначаем ему домен и не подключаем весь проект к общей predefined-сети.

## Поставка

1. Pull request: проверка Compose, тесты скриптов, сборка Nginx и HTTP-проверка контейнера.
2. Push в main: те же проверки, затем публикация образа в собственный Registry.
3. Отдельное задание workflow обновляет WEB_IMAGE в Coolify полным адресом образа с digest и запускает деплой.
4. Проверка /health ожидает SHA исходного кода и идентификатор конкретной сборки. Это проверка веб-компонента, не готовности будущего backend или базы.

Публикация и деплой включаются отдельно после подготовки Registry и Coolify. Git-автодеплой приложения в Coolify отключён. Watchtower не управляет контейнерами проекта. Одновременные production-workflow выполняются последовательно.

## Данные и границы доступа

- Секреты не входят в Git и Docker build context. GitHub Secrets хранит доступы CI, Coolify — runtime-настройки.
- Registry использует собственный htpasswd с bcrypt поверх внешнего HTTPS. Базовая авторизация не разделяет права push/pull по пользователям.
- Публичный API появится только через веб-прокси; прикладная валидация и защита запросов относятся к будущему backend.
- Данные заказов предназначены для хранения на сервере. Код приложения, интеграции и логирование должны соблюдать это ограничение.
- Постоянные тома переживают замену контейнера, но не заменяют резервные копии.
- Остановленный Registry не останавливает работающий контейнер приложения, но мешает скачиванию образов при новых развёртываниях.
