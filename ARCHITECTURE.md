# Архитектура Customer Orders Platform

Customer Orders Platform принимает заявки на автоматизацию бизнеса. Публичная часть — каталог услуг и форма; управление услугами, заявки и Swagger доступны администратору.

## Компоненты

```text
Браузер → HTTPS → Traefik → Nginx
                            ├─ frontend и локальные ресурсы Swagger
                            ├─ /health → метаданные web
                            └─ /api → FastAPI → PostgreSQL, schema orders
                                        ├─ services
                                        ├─ applications
                                        └─ behavior_metrics

pgAdmin → PostgreSQL
   ↑ loopback VPS ← SSH-туннель администратора

GitHub Actions → собственный Registry → постоянный том образов
       └─ Coolify API → WEB_IMAGE и BACKEND_IMAGE с digest → деплой
                          └─ подтверждение version/release у обоих компонентов
```

Registry и приложение — независимые ресурсы Coolify. Traefik завершает HTTPS; Nginx сохраняет префикс /api и передаёт запросы backend без перенаправления завершающих слешей. Порты backend и PostgreSQL не публикуются на VPS. Только backend и pgAdmin соединены с внутренней сетью database. PostgreSQL не подключён к общей сети приложения.

## Модель данных

Услуга содержит название, описание, slug, активность и диапазон бюджета в целых рублях. Заявка ссылается на услугу и хранит снимок её названия. Деактивация услуги не удаляет старые заявки. Обязательны имя, описание и хотя бы один контакт. Предпочтительный канал требует соответствующих контактных данных. Неизвестный бюджет хранится как NULL.

Базовые метрики связаны с заявкой один к одному по application_id: время до отправки, число попыток и повторное посещение. Выбранная услуга определяется через заявку. Повторное посещение определяется локальным флагом браузера без контактных данных. Метрики являются клиентскими оценками.

Отдельная аналитика посещений работает после согласия: visits, visit_days, analytics_batches, behavior_events и analytics_daily. Посещения не связываются с контактами заявок. События кликов/курсора сохраняются до 30 дней, суточные агрегаты — до 365 дней. IP, fingerprint и значения полей не сохраняются. Приём пакетов идемпотентен; фоновые задачи чистят данные раз в час. Подробности: docs/ANALYTICS.md.

Автоматическая оценка заявки сохраняется вместе с версией правил; ручной приоритет и комментарий хранятся отдельно. Сортировка учитывает эффективный приоритет и возраст заявки. Правила: docs/PRIORITIZATION.md.

Создание заявки и метрик выполняется одной транзакцией. UUID Idempotency-Key защищает от дублирования при повторной или одновременной отправке. С тем же ключом разрешён только тот же набор бизнес-данных; счётчик попыток может увеличиваться. Публичный ответ не содержит контактов.

## База и миграции

Администратор один раз создаёт роль orders_app и схему orders в существующей базе. Роль не является superuser и не создаёт базы или роли, но владеет своей схемой для применения миграций. Backend не подключается административным пользователем.

Миграции Alembic запускаются перед HTTP под транзакционной advisory-блокировкой PostgreSQL. Ошибка останавливает старт. Новые таблицы не затрагивают public и служебные таблицы других ресурсов. Тома сохраняются при обновлении. Откат образа не откатывает данные и миграции.

## API и административный доступ

GET /api/services и POST /api/applications доступны публично. Все /api/admin-маршруты защищены JWT в HttpOnly Secure SameSite cookie, включая docs и openapi.json. JWT проверяется по действующему admin_sessions и активному admins; изменяющие запросы требуют CSRF. Пароли — Argon2id. Одноразовое приглашение выдаётся серверной командой только до создания первого администратора; операция атомарна. Восстановление выполняется интерактивной командой. Подробности: docs/ADMIN.md.

Статическая панель /admin использует тот же origin и backend без отдельного фреймворка. Внешняя работа только через HTTPS. Swagger загружается с собственного сервера без CDN и внешнего валидатора, использует cookie текущего браузерного сеанса и локальный CSRF helper. Контракт: docs/API.md и docs/openapi.json.

Nginx ограничивает тело запроса и общий поток создания заявок. Это не персональная квота и не полноценная защита от распределённого злоупотребления. Логи не содержат тел, query, паролей и контактов. Администраторы Docker и Coolify имеют доступ к конфигурации и должны считаться доверенными.

## Поставка и проверка

GitHub Actions проверяет Compose, поведение скриптов, frontend и API с настоящей PostgreSQL. Затем собирает web/backend, запускает изолированный стек и проверяет полный сценарий через Nginx, включая отказ и возврат БД. Публикуются уже проверенные образы без повторной сборки.

Deploy передаёт оба digest одним bulk-запросом к Coolify, запускает развёртывание и ждёт совпадения version/release на /health и /api/health. Это подтверждает web, backend и соединение с БД; не проверяет внешние интеграции, которых сейчас нет.

Флаги BACKEND_DEPLOY_READY и ADMIN_DEPLOY_READY предотвращают автоматический переход до подготовки новых настроек. Auto Deploy из Git и Watchtower для приложения выключены. Production-запуски Actions выполняются последовательно.
