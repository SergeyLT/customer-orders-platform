# Запуск приложения и обновление инфраструктурного релиза

Приложение состоит из web и backend. Registry остаётся отдельным ресурсом Coolify. Все примеры используют условный домен `example.com`.

## Перед первым push

Repository variable `BACKEND_DEPLOY_READY` оставьте отсутствующей или `false`. Новая версия workflow будет проверять и публиковать оба образа, но не запустит неподготовленный backend автоматически. Существующий сайт и PostgreSQL продолжат работать до явного Redeploy. Для защиты от старых workflow, запущенных до изменения файла, дополнительно поставьте `DEPLOY_ENABLED=false` и дождитесь окончания уже начатых деплоев.

## Подготовка существующей базы

Не удаляйте том PostgreSQL и не меняйте имя существующей базы. Сделайте резервную копию перед первым применением миграций.

Backend работает как `orders_app` и создаёт таблицы только в собственной схеме `orders`. Он не использует административного пользователя PostgreSQL. Роль имеет право менять свою схему, чтобы применять миграции, но не является superuser и не может создавать роли и базы.

На VPS определите точное имя контейнера PostgreSQL нужного приложения. Скопируйте туда только скрипт `scripts/create_app_database_user.py` или выполните его из checkout на VPS. Нужны Python 3 и доступ к Docker, сторонних пакетов не требуется:

```sh
python3 scripts/create_app_database_user.py --container <postgres-container-name>
```

Если база или административный пользователь отличаются от значений по умолчанию, добавьте `--database <name> --admin-user <name>`. Пароль роли приложение запросит интерактивно дважды; он не передаётся через аргументы процесса. В Coolify сохраните его как `APP_DB_PASSWORD`.

Скрипт создаёт роль и схему без удаления существующих данных. При существующей роли он остановится; `--replace` предназначен для явной ротации её пароля. Уже существующая схема orders должна принадлежать этой роли. Не используйте скрипт для посторонних ресурсов сервера.

Для новой пустой базы: сначала можно запустить только PostgreSQL из подготовленной инфраструктуры, создать роль, затем развернуть все компоненты. В локальном `compose.local.yaml` роль создаёт init-скрипт при первом создании отдельного локального тома.

## Параметры приложения в Coolify

Ресурс из Git использует `/compose.coolify.yaml`, ветку `main`, Auto Deploy выключен, Connect To Predefined Network выключен. При переходе обновите Compose кнопкой Reload Compose File, сохранив существующий ресурс и его тома.

В runtime-настройках приложения должны быть:

| Переменная | Назначение |
| --- | --- |
| `WEB_IMAGE` | Полный digest web из Summary нового workflow |
| `BACKEND_IMAGE` | Полный digest backend из того же workflow |
| `POSTGRES_DB` | Существующая база, обычно customer_orders |
| `POSTGRES_USER`, `POSTGRES_PASSWORD` | Существующие административные параметры PostgreSQL, не менять при переходе |
| `APP_DB_PASSWORD` | Пароль созданной роли orders_app |
| `ADMIN_USERNAME` | Администратор API, по умолчанию admin |
| `ADMIN_PASSWORD` | Новый отдельный пароль от 24 символов для Swagger и административного API |
| `PGADMIN_DEFAULT_EMAIL`, `PGADMIN_DEFAULT_PASSWORD`, `PGADMIN_HOST_PORT` | Существующие настройки pgAdmin |

Оба digest должны относиться к одинаковым Version и Release. Не используйте нулевые значения из `.env.example` и не переключайтесь на latest.

Пароль можно сгенерировать локально: `python -c "import secrets; print(secrets.token_urlsafe(24))"`. Доступы API, pgAdmin, БД и Registry должны различаться.

Назначьте домен **только** компоненту web: `https://orders.example.com:8080`. PostgreSQL и backend не публикуют host-порты; pgAdmin остаётся на loopback. Backend должен быть в сетях default и database, PostgreSQL — только database. Проверьте deployable Compose после обработки Coolify.

Миграции backend автоматически применяются перед запуском HTTP. Ошибка роли, доступа или миграции останавливает запуск; HTTP-процесс не объявляет готовность. Не отключайте эту проверку и не удаляйте том для исправления ошибки.

Coolify может передавать общие runtime-переменные нескольким компонентам. Статический процесс Nginx запускается с очищенным окружением; после миграций backend выполняет exec с разрешённым набором переменных без административного пароля PostgreSQL. Docker-конфигурация по-прежнему доступна администраторам сервера и не является хранилищем секретов с изоляцией от Docker-admin.

## Первый запуск

1. Дождитесь успешных checks и publish. Возьмите оба digest из Summary.
2. Подготовьте роль БД и новые переменные, обновите Compose и домен.
3. Выполните ручной Deploy приложения.
4. Проверьте `/health` и `/api/health`: оба должны вернуть одинаковые version и release; component — web и backend соответственно.
5. Откройте `https://orders.example.com/api/admin/docs`. Вход выполняется учётными данными ADMIN_USERNAME/ADMIN_PASSWORD. Ресурсы Swagger загружаются с этого же сайта, внешние CDN не используются. В Swagger при необходимости нажмите Authorize и укажите те же HTTP Basic credentials.
6. Создайте три услуги из [API.md](API.md), убедитесь, что GET `/api/services` возвращает весь список.
7. Отправьте заявку через форму и проверьте её в административном API или pgAdmin: база customer_orders → schema orders → tables applications и behavior_metrics. Метрики связаны с заявкой по application_id.

Обычный пользователь видит только подтверждение и номер своей отправки. Список заявок и контакты недоступны без административной авторизации. Публичный административный интерфейс должен обслуживаться только по HTTPS; для дополнительного ограничения можно использовать VPN/SSH и правила прокси.

## Автоматические релизы

После первого успешного запуска задайте repository variables `PUBLISH_ENABLED=true`, `DEPLOY_ENABLED=true`, `BACKEND_DEPLOY_READY=true`.

GitHub Environment production содержит `REGISTRY_HOST`, `COOLIFY_URL`, `COOLIFY_APP_UUID`, `PUBLIC_BASE_URL`; Secrets — `REGISTRY_USERNAME`, `REGISTRY_PASSWORD`, `COOLIFY_TOKEN`. UUID должен указывать на приложение, а не Registry. Токен требует write и deploy.

Deploy-job передаёт WEB_IMAGE и BACKEND_IMAGE одним PATCH `/api/v1/applications/{uuid}/envs/bulk`, затем вызывает POST `/api/v1/deploy`. Фактическое завершение подтверждается совпадением version/release на двух health-маршрутах. Настройте поддержку bulk API и оба runtime-поля до включения флагов.

Тестовый artifact содержит уже проверенные образы: publish-job загружает и отправляет их без повторной сборки. Частичный повтор jobs использует метаданные из того же artifact. Git-автодеплой Coolify для приложения остаётся выключенным.

## Проверка и откат

При ошибке посмотрите логи конкретного backend-контейнера и статусы сервисов. В штатных логах приложения нет исходных тел, query, контактов или паролей. Общий лимит создания заявок и размер тела заданы в Nginx; при росте нагрузки пересмотрите их осознанно.

Для отката отключите автоматический deploy, установите оба digest предыдущего согласованного релиза и выполните Redeploy. Откат кода не откатывает миграции и данные. Первичная миграция добавляет только новую схему приложения и не изменяет существующие таблицы других схем; будущие изменения должны оставаться совместимыми либо иметь отдельную процедуру восстановления.

Перезапуск сервисов и обновление образов не должны удалять тома. `down --volumes` применяется только к явно созданным локальным тестовым проектам, не к рабочему ресурсу.
